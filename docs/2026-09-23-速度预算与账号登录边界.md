# 速度预算 与 "账号密码登录" 的边界（2026-09-23）

## 一、你问的两件事

1. **速度不够快**：国庆的票几乎一秒没，现在这速度抢不到 → 能不能再优化？
2. **能不能用账号密码登录 12306**，这样就能挂定时任务，不用本人扫码？

---

## 二、账号密码登录：**不做**（这不是能力问题，是边界问题）

三条理由，任何一条单独成立都足以否决：

1. **安全**：要自动登录就必须把**你的 12306 密码**存在本地。这是个跑在你自己电脑上的小工具，
   一旦被读取（恶意软件、误传目录、日志泄漏）就是账号级别的损失。工具不应持有你的密码。
2. **风控**：12306 的密码登录几乎必然触发**滑块 / 短信验证**——自动化根本过不去，
   而且"脚本尝试密码登录"这个行为本身就容易被判为异常，**可能把账号打进风控**，得不偿失。
3. **设计边界**：本工具的既有原则是「**本人扫码，工具不代输密码或验证码**」，
   README 与代码门控都是按这条写的。改成账号密码登录等于推翻这条边界。

### 那"无人值守"怎么办？

- **尽量晚扫码**：开售前 **20~30 分钟**登录，让会话在开抢时是"新鲜"的。
  这也是目前数据支持的用法（17:03 扫码、17:12 开抢 → 成功；扫码后挂机 100 分钟 → 失败）。
- **定时提醒**：已支持（本次就给你设了 15:30 的提醒），提醒你扫码 + 一键启动，但**扫码这一步必须本人**。

## 三、速度：先量化，再说能不能优化

### 下单路径的固定等待（我们自己的开销）

| 位置 | 固定等待 |
| --- | --- |
| `select_ticket_type` | 300 ms |
| `select_seat` | 300 ms |
| `handle_popups`（仅在真的处理弹窗时） | 800 ms |
| 提交后结果轮询 | 400 ms |
| 其他 | 500 ms |
| **合计（我们自己的开销）** | **约 1.5~2.3 秒** |

### 真正的大头：12306 自己的页面加载

全新导航下单需要**两次页面加载**（结果页 → 确认页），实测"确认页核对"这一步：
**2.39s（复用预热页面）～ 7.86s（全新导航）**。

### 结论（不粉饰）

> **浏览器方案的地板就是 5~8 秒。** 对于"1 秒售罄"的国庆热门车次，**我们抢不到。**
> 能优化的只是我们自己那 1~2 秒，动不了官方页面加载。

### 真正能提高成功率的三个方向

1. **候补购票**（官方支持、最推荐）：售罄后仍可排队，热门车次的候补成功率远高于硬抢；
2. **尽量晚扫码**：让下单资格保持"新鲜"（见下节）；
3. **避开最热车次/时段**：同一线路里冷门车次的余票窗口长得多。

### 不建议的方向

**复刻 12306 内部接口**（跳过页面直接发请求）确实能快，但：
接口随时变、签名随时改 → 极其脆弱；且这种高频直连请求**正是风控重点打击对象**；
本质就是爬虫——本工具刻意不走这条路。

## 四、还有个更根本的问题挡在前面

五次现场记录显示：**会话越老，下单越可能被拒**（而 `checkUser` 一直报有效）：

| 会话年龄 | 保活 ping | 结果 |
| --- | --- | --- |
| ≤ 36 分钟 | ≤ 2 次 | ✅ 全部成功 |
| ≥ 100 分钟 | ≥ 22 次 | ❌ 全部失败 |

也就是说：**挂机越久越抢不到**——这直接命中你"提前 1-2 小时启动"的用法。
在分清是"会话年龄"还是"保活 ping 次数"之前，速度优化都是次要的。

（区分实验：跑 25 分钟等待的演练 ≈ 8 次 ping；再跑一组"不发 checkUser、只做页面访问"的对照。）

## 五、A/B 复验结果（19:38）：**"复用预热页面"被否决，那 5 秒省不掉**

```
[19:38:00] 命中 G531 二等座！开始演练…
[19:38:00] 点"预订"前会话校验：True
[19:39:08] 确认页核对 68.44s（超时）→ CANCELLED
｜诊断：点击后 URL=https://kyfw.12306.cn/otn/leftTicket/init?...（仍是结果页，没跳转）
        页面摘录=...我的12306 | 您好，示例乘车人 | 退出...
```

**诊断第一次给出了有信息量的报错**，两个关键事实：

1. **点击后 URL 仍是结果页** → 点"预订"**根本没有跳转**；
2. **页面仍显示"您好，示例乘车人 | 退出"** → **会话是好的，没掉线**。

**结论：复用预热页面的"预订"按钮点了无效**（该页的预订凭证是放票前生成的），
与会话无关。→ **必须重新导航，那约 5 秒省不掉。** 原先的修复是对的。

## 六、由此修正：失败其实有两种不同模式

| 模式 | 触发条件 | 症状 | 状态 |
| --- | --- | --- | --- |
| **A｜凭证过期** | 复用放票前加载的预热页面 | 点"预订"无跳转，**会话不受影响** | ✅ 已修（改为重新导航） |
| **B｜下单资格失效** | 会话过老（18:43 那次已 100 分钟） | 确认页打不开，**且会话被作废** | ❌ 未解决 |

并且：19:38 这次会话已 **40 分钟**，`checkUser` 仍有效、也没被作废
→ 所以"36 分钟阈值"的说法需要修正；**模式 B 目前只有 18:43 一个样本**，证据还很弱。
