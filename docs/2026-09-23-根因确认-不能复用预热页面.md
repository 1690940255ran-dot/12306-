# 根因确认：抢票失败是"复用预热页面"导致的（2026-09-23 17:00 现场 A/B）

## 一、现场日志（一次运行内完成 A/B 对照）

```
[16:55:00] 预热：打开官方查询结果页…（此时 62 个车次仍是 *，未放票）
[17:00:10] 命中 C3782 二等座！开始下单…
[17:00:11] 点“预订”前会话校验：True          ← 会话此刻是好的
[17:01:24] 下单失败，且检测到登录已失效       ← 复用预热页面 → 失败 + 会话被作废
[17:03:46] 登录已恢复，正在重试下单…（全新导航）
[17:03:49] 重试结果：确认页席别选项中没有“二等座”：['一等座（¥76.0元）']  ← 成功打开确认页！
```

**同一次运行、同一个会话、同一趟车 C3782：**

| 做法 | 结果 |
| --- | --- |
| **复用预热页面**（`use_current_page=True`） | ❌ 点"预订"失败，**会话被作废** |
| **全新导航**（`use_current_page=False`） | ✅ **成功打开官方确认页** |

这是一个干净的 A/B 对照，不再依赖任何猜测。

## 二、根因

**预热发生在放票前**（16:55 加载结果页时，全部车次还是 `*` 未开售）。
那一页里"预订"按钮携带的凭证是**放票前**的。到 17:00 放票后，
行内容虽然刷新成了"有票"，但**页面持有的预订凭证已经过期**；
点"预订"被服务端拒绝，并连带把会话作废（页面随后显示"请登录注册"）。

**这解释了此前所有矛盾现象：**

| 场景 | 预热页面加载时 | 结果 |
| --- | --- | --- |
| 9-22 12:45 真实抢票 | 放票前（`*`） | ❌ 失败 + 掉线 |
| 9-23 12:45 真实抢票 | 放票前（`*`） | ❌ 失败 + 掉线 |
| 9-23 17:56 演练 | **已开售**（有票） | ✅ 确认页 2.39s 打开成功 |
| 9-23 17:00 **重试（全新导航）** | 放票后 | ✅ **确认页打开成功** |

同时也解释了为什么"保活正常、会话校验 True"却仍然失败——
问题不在会话，而在**那一页的预订凭证**。

## 三、修复

`application/rush_service.py` · `_place_order`：**下单一律重新导航，不再复用预热页面**
（`use_current_page=False`）。命中检测仍走预热页面的快速轮询（2 秒一轮，不受影响），
只有"点预订"这一步重新加载页面。

`config.py`：`post_hit_settle_seconds` 默认改回 **0**——实测加 1.5 秒等待并不能解决该问题，
真正原因是不复用预热页面；该配置保留给"表格渲染极慢"的极端情况。

回归：**167 项单测 + 16 项回归审计全 PASS**
（新增 `test_order_uses_fresh_navigation_not_preheated_page`）。

## 四、为什么这次仍然没拿到票

不是机制问题，是**时间被耗掉了**：

```
17:00:11  首次尝试失败（复用预热页面，耗 65 秒等待超时）
17:01:24  弹出登录窗等扫码
17:03:46  你扫码完成，重试开始（耗时 2 分 22 秒）
17:03:49  确认页打开，但二等座已售罄，只剩一等座 ¥76
```

工具**正确地拒绝**了改席别下单（宁可不下，也不替你买错席别）。

**修复后**流程将是：命中 → 重新导航（约 2~3 秒）→ 确认页 → 提交，不再有"必然失败 + 掉线 + 等扫码"的 3.5 分钟损耗。

## 七、附带修复：席别不符也会锁死目标

17:00 那次重试失败原因是"确认页席别选项中没有二等座"（**官方侧未收到任何提交动作**），
但 `_needs_user()` 统一使用 `reason_code="needs_user"`，不在"确定未触达官方"的名单里
→ `order cancel` 拒绝 → **该购票目标被永久占住**。

**修复**：`_needs_user()` 新增 `reason_code` 参数，默认 `needs_user_prepare`
（确认页阶段失败 = 官方侧零动作，可安全本地取消）；只有**提交动作之后**才转人工的
（官方返回 NEEDS_USER）才显式传 `needs_user`。同时把 `needs_user_prepare`
加入 `_NEVER_SENT_REASON_PREFIXES`。

回归：**167 项单测 + 16 项回归审计全 PASS**。

## 九、附带改进：起售时间不再恒为 null

`query_sale_time` 一直返回 `sale_time=None`，理由是"官方数据无法证明某乘车日**哪天**开售"，
所以拒绝把时刻拼到日期上——**这个保守是对的，但代价是用户连"几点起售"都拿不到**，
只能手工去查（本次验证里我都是自己去读官方接口）。

**改动**（不推翻原有保守设计）：

- `SaleTimeResult` 新增 **`sale_clock`**（"HH:MM"）：官方规则记录
  `sale_time=HHMM` 且有效期 2010-01-01~2099-12-31，说明它是**车站的固定每日属性**，
  与乘车日无关，可以安全给出；
- `sale_time`（完整时间戳）**行为不变**——仍只在已知开售日时才给出，不推算；
- `sale-time fetch` 现在会额外返回 `sale_clock`，可直接用于填写抢票的 `sale_at` 时间部分。

回归：**170 项单测 + 16 项回归审计全 PASS**（新增 `StationSaleClockTests` 3 项）。
