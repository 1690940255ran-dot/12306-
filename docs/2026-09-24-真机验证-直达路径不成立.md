## 一、速度项：**我的"直达确认页"优化在真实环境不成立 → 已撤回**

### 1.1 第一轮实测（21:27）——直达全部拼不出 URL

```

第 2 轮 direct FAIL   ...
第 2 轮 click  OK      1469 ms
第 3 轮 direct FAIL   ...
第 3 轮 click  OK      1407 ms
```

### 1.2 根因一：token 不是字母数字（我的校验写错了）

真机 onclick 原文：

```
checkG1234('DLeyjxKqfQ6i8JhIZjL8haWLVVGqZxmJQg0R63kbO%2Flvk3vYlVQzKlK9p4r4HUct9HhmLXOfuDL3
%0A%2FtOsBM%2FLde9GeR2qjo96RWspY3AyJAeVphuZ3G7GQZXa22nFB5Ao9PNu%2B6XwqhiuYIXjm27T80J1
...
%0AvBKLxX8KDspPxxSFxUlI5RY5QHyaTNycG2rQBA%3D%3D','11:32','55000C385602','UDH','NJH',
'','O0099W0099','SHH','NJH');
```

- token 是**已百分号编码的 base64**（含 `%2F` `%2B` `%3D` **甚至 `%0A` 换行**）；
- 我原来按 `[0-9A-Za-z]{8,64}` 校验 → **真实环境 100% 判定失败**；
- 参数布局本身是对的：`token, 开车时刻, 内部车次号, 出发电报码, 到达电报码, …`。

→ 已修正为"未保留字符 或 `%HH`"并**原样拼接（不许二次编码）**，同时保留"再编码"变体用于 A/B。

### 1.3 根因二（决定性）：官方"预订"是 **POST 表单 + 服务端会话上下文**

抓包（`.runtime/probe_direct_url_real.py`，点击官方"预订"）：

```
POST https://kyfw.12306.cn/otn/confirmPassenger/initDc?N
     body: _json_att=
     referer: https://kyfw.12306.cn/otn/leftTicket/init?...   ← 结果页
POST https://kyfw.12306.cn/otn/confirmPassenger/getPassengerDTOs
     body: _json_att=&REPEAT_SUBMIT_TOKEN=82901f71724a0f34975f510530099ebe
```

**关键事实：URL 里没有任何车次/区间/token 参数**（`官方请求参数键: []`）——
待预订车次存在**服务端会话**里，确认页靠它初始化。

因此"用 GET 拼 `train_no/leftTicket/...` 直达"根本不是官方的调用方式。实测两种 token 处理：

```
变体 raw       → 最终 URL 仍是那个 GET URL，正文="…您好，陈健…**系统忙，请稍后重试**…"，#submitOrder_id 不存在
变体 reencoded → 同上
```

第二轮探针（21:35，各 2 次共 6 次直达尝试）：**全部 FAIL**，点击路径 2 次成功（2922 / 5219 ms）。

### 1.4 结论与处置

| 项 | 结论 |
| --- | --- |
| "直达省 2~5 秒" | ❌ **不成立**，此前的说法作废 |
| 代码处置 | `order_fastpath` **默认改为 False**（打开只会白花一次导航后回退）；代码与探针保留，供"两步 POST"方案复验 |
| 推论（未验证） | 想省这一步只剩"复刻官方两步：`POST /otn/leftTicket/submitOrderRequest`（带 secretStr）→ `POST initDc`"。这属于项目原则里刻意不走的"复刻内部接口"路线，且**尚未验证**，不宣称可行 |
| 真实可用路径耗时 | 结果页 → 确认页可交互：**1407 / 1469 / 2110 / 2922 / 5219 ms**（5 次有效样本，中位数 ≈2.1 s，波动极大） |

> ⚠️ 口径提醒：探针测的是"结果页→确认页可交互"这一段；
> 主程序日志里的"确认页核对+提交 X.XXs"是**另一段**（含乘车人/席别填写与官方提交弹窗倒计时），
> 两者**不能直接对比**。历史那条 7.86s 与本次 2.1s 不是一个东西。

### 1.5 所以"速度够不够"

**不够**，而且比我上次说的更差：

- 本次真机测出的可用路径就要 **1.4~5.2 秒**（还没算填写乘车人/席别与官方提交倒计时）；
- 到点抢票时官方负载更高，只会更慢；
- 我承诺的"省 3~6 秒"**没有兑现**（唯一的净加速只剩"固定等待压缩"约 1 秒级）；
- 对"一秒售罄"的热门车次，浏览器方案依然抢不到。**正解仍是官方候补。**

## 二、保活项：真机 70 分钟长测 → **结论：保活不够（只保住了表面登录态）**

**实验**：21:41 起按 GUI 同款保活（每 240 秒：`checkUser` + 一次官方页面轻量访问 +
重新加密落盘）连续跑 **70 分钟（18 次续期）**，然后用**稳妥路径**（重新导航结果页 +
点"预订"）验证确认页能否打开。

### 2.1 结果

| 阶段 | 观测 |
| --- | --- |
| 保活期间（18 次续期） | **全部** `保活正常：下单登录态有效` + `会话已加密保存`（`checkUser flag=true`） |
| 70 分钟后：点"预订" | ❌ **没有跳转**——72.4 秒后超时失败；`点击后 URL 仍 = /otn/leftTicket/init?...`（结果页） |
| 失败后立刻查 `checkUser` | ❌ `flag=false` → **会话在"点击被拒"的同时被官方作废**（与 09-23 记录同型） |

### 2.2 排除性证据：不是"没票"

失败后立即重新查余票（只读，不需要登录）：

```
C3856 一等座 COUNT 2 / COUNT 8，二等座 AVAILABLE（有），无座 SOLD_OUT
全站可购席别单元：89 / 196 条票额
```

**该车次仍有票、预订入口仍在，但会话点不进去** → 失败属于**会话/下单资格**问题，
不是票量变化、也不是页面结构变化。

### 2.3 因此修正两条旧结论

1. **"保活能把会话维持住"只对表面层成立**：本次保活方式已升级为
   "checkUser + 真实页面访问 + 重新落盘"，**18 次续期后下单资格依然失效**。
   所以"高频 checkUser 被判脚本"这个假设**不是主因（至少不是全部）**；
   更可能是**下单资格本身有时效**（约 1 小时内）。
2. **2026-09-23 把"点预订失败"归因于"复用预热页面凭证过期"是不完整的**：
   本次用的是**全新导航**（当时认定的正确做法），70 分钟会话下**同样失败**。
   → 「会话老化（模式 B）」才是那类失败的主因，与"复用页面"关系有限。

### 2.4 汇总：会话年龄 vs 结果（含本次真机）

| 会话年龄 | 保活次数 | 结果 |
| --- | --- | --- |
| 4 分钟 | 1 | ✅ 成功（09-23 19:02 演练） |
| 9 分钟 | 2 | ✅ 成功（09-23 17:12） |
| 36 分钟 | 0 | ✅ 真实订单成功（09-21 11:25） |
| **70 分钟** | **18** | ❌ **本次：车次有票，点预订不跳转，随后 flag=false** |
| 100 分钟 | ~30 | ❌ 09-23 18:43 |
| 112 分钟 | ~22 | ❌ 09-22 12:45 |

**可复现的规律：≤36 分钟可用；≥70 分钟不可用。** 阈值落在 36~70 分钟之间，
且**保活（含真实页面访问）无法把它推过 70 分钟**。

### 2.5 对你的用法意味着什么（重要）

- ❌ "提前一小时打开、挂机到点抢" → **实测会失败**（70 分钟组就是反例）。
- ✅ 正确做法：**开抢前 20~30 分钟内扫码登录**（落在 ≤36 分钟的安全窗内），
  然后让保活维持到开抢；保活在 150 秒间隔下足够覆盖这半小时。
- ⚠️ 这也意味着"早上出门前先登录、晚上回来抢"这种用法**不可行**，
  会话活不过夜、下单资格也撑不过一小时。

## 三、两步 POST：已实现，等一次真机 A/B（2026-09-24 深夜）

用户明确授权后，按抓包结果复刻了官方"预订"的真实链路：

```
① POST /otn/leftTicket/submitOrderRequest     ← 把车次/区间/token 写入服务端上下文
   body（字段与顺序照官方抓包）：
     secretStr=<token 原样>&train_date=…&back_train_date=…&tour_flag=dc
     &purpose_codes=ADULT&query_from_station_name=…&query_to_station_name=…
     &bed_level_info=&seat_discount_info=<onclick params[6]>&undefined=
② 表单 POST /otn/confirmPassenger/initDc?N    ← body 只有 _json_att=（与官方同款请求）
```

实现位置与接缝：

| 位置 | 作用 |
| --- | --- |
| `left_ticket.submit_order_request_body()` | 拼①的表单体；**secretStr 原样插入**（它已百分号编码，二次编码会被官方拒） |
| `adapter.prepare_order_two_step()` | 页面内 fetch ① → 表单 POST ② → 等确认页 → 走原有核对链 |
| `booking_service._prepare_order_intent()` | 顺序：两步 POST → GET 直达 → 复用页 → 重新导航；只有"这一步没走通"才回退 |
| `config.order_two_step`（默认 **False**） | 打开时才在热循环回读命中行参数；失败自动回退，绝不丢单 |
| `scripts/probe_confirm_speed.py` | 新增 `two_step` 测量项，与 `click` 同一口径（结果页出发 → 确认页可交互） |

已完成的验证：**207 项单测 + 18 项审计全绿**（含"字段与官方抓包一致""token 不被二次编码"
"两步失败必须回退且仍能下单""默认关闭"）。
