## 二、缺陷 1（已修复）：抢票命中检测因“混淆函数名”永久失效

### 现象
用户观察：抢票页面**反复查询**，明明页面上有 C432，却一直不命中、不下单。

### 根因
官方余票结果页“预订”按钮的 `onclick` 处理函数名是**运行时混淆**的，本次实测为
`checkG1234(...)`，而代码把区间解析**写死为函数名 `getSelected`**：

- Python `segment_of_row()`：`re.search(r"getSelected\(", row_html)`
- 页面内观察器 JS：`if (oc.indexOf('getSelected') >= 0) { ... }`

函数名不匹配 → 区间解析恒为 `None` → 观察器 `if (!seg || ...) return false` 直接否决该行
→ **永不命中**（且静默，无任何日志）。

对比：2026-09-19 现场该函数名恰好是 `getSelected`，所以当时可用；官方改名后即静默失效。

### 证据
同一车次 C432 在同一结果页有两行（灵活行延伸段）：

| 行 | 预订 onclick 区间参数 | 实际确认页 |
| --- | --- | --- |
| #42 | `NJH` → `YLH` | 南京 → **扬州**（非目标） |
| #43 | `NJH` → `UDH` | 南京 → **江都**（目标） |

`onclick` 参数结构（函数名无关）：`('<token>','18:12','540000C43200','NJH','UDH','','O0090M0090W0090','NJH','QOU')`
→ 第 2 个参数是开车时刻 `HH:MM`，第 3 个是车次号 `train_no`，第 4/5 个是区间电报码。

### 修复
`src/railassist/adapters/browser/left_ticket.py`：

1. 新增 `_booking_params()`：**不依赖函数名**，改为按参数结构识别预订锚点
   （第 2 参数 `\d{2}:\d{2}`、第 3 参数为车次号），据此取 `params[3], params[4]` 作为区间；
   同时天然排除同行 `myStopStation.open(...)` 等非预订锚点。
2. 观察器 JS 采用同样的结构识别。
3. 观察器 JS 与 Python 语义对齐：**区间解析不到时不再据此否决该行**
   （改为 `if (seg && 不匹配) return false;`），与 `poll_train` 一致；乘降站最终由确认页复核。

### 修复验证（只读）
```
行 C432: segment=('NJH','YLH')  二等座格='有'
行 C432: segment=('NJH','UDH')  二等座格='有'
read_hit -> C432          ← 修复前为 None
```
扬州行被正确跳过，江都行命中。修复后实测抢票立即命中并进入下单。

## 三、缺陷 2（已修复）：`QUEUED → RECONCILING` 状态迁移缺失

### 现象
```
order reconcile --attempt ff535151… --adapter browser
→ 错误：不允许的订单状态变更：QUEUED → RECONCILING
```

### 根因
`BookingService.reconcile()` 明确把 `QUEUED` 列为可核对状态并执行
`QUEUED → RECONCILING`，但 `domain/states.py` 的 `ORDER_TRANSITIONS[QUEUED]`
允许集合里**没有 `RECONCILING`**。二者不一致 → 排队中的订单永远无法核对。

### 修复
`ORDER_TRANSITIONS[OrderStatus.QUEUED]` 增加 `OrderStatus.RECONCILING`。
修复后事件链出现 `QUEUED → RECONCILING(reconcile_start)`，核对流程可执行。

## 四、缺陷 3（已修复）：提交结果把风控“排队”误判为订单排队

### 现象
提交后 `outcome=QUEUED`（“官方显示排队处理中”），但官方“未完成订单”页为**空态**（无订单）
→ 说明该 QUEUED 是**误报**：C432 二等座当时是“有”票，正常不应排队。

### 根因
`classify_submit_text()` 只要提交后新增文本含 `排队` 或 `正在处理` 就判 `QUEUED`。
12306 的风控/限流提示同样会出现这类字样（如“当前排队人数较多，请稍后重试”），
于是被误判成“订单排队中”。

### 修复（`adapters/browser/order_page.py`）
1. 新增 `keywords_throttle`（稍后重试/稍后再试/请重试/人数较多/人数过多/系统繁忙/网络繁忙/
   访问量过大/请求过于频繁/繁忙），在“排队”判定**之前**命中即返回 `UNKNOWN`
   （只核对、绝不重提）。
2. `QUEUED` 与 `UNKNOWN` 的 message 追加**原文摘录**（≤60 字），便于事后定位真实返回文本。

## 五、官方“未完成订单”页结论：本次为空态（无订单）

先前把“页面只渲染通用框架”当作异常，经比对**证伪**：

- 实测页面 innerText（规范化后 433 字）与工具自带空态样本
  `tests/fixtures/orders_empty_sample.txt` **逐字符完全相同**。
- 该样本正是项目记录的“未完成订单为空”的状态。
- 因此 `reconcile` 返回 `UNKNOWN` 属**设计预期**（“不能仅凭未完成列表没找到断定没有订单”），
  但结合空态样本可判定：**本次未生成订单**。

已补充单测 `test_empty_orders_page_is_unknown_not_a_conclusion` 固化该行为（空态 → UNKNOWN，
不得断言“没有订单”）。
