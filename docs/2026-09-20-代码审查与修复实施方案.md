## 1. 结论与本次交付

项目已经包含 CLI、PySide6 GUI、查询调度、浏览器登录、普通订单、模拟候补、数据库迁移和抢票流程，并非最初的空框架。领域层、应用层、适配器分层值得保留，但浏览器生命周期、两套调度路径和订单可信状态之间没有统一起来。现有测试通过不能证明真实抢票流程没有问题。

最影响用户体验的根因：

1. **重复扫码有明确的本地原因**：GUI 抢票线程每次新建浏览器，且显式设置 `remember=False`；GUI 的登录、查票、下单又各自创建并关闭 Application。保存了会话也没有在抢票路径中复用。不能把所有重登都归因于官方过期。
2. **提前打开页面的收益被后续流程抵消**：命中后先在同一标签页导航到账户页检查登录，并固定等待 2.5 秒，再完整导航回查询页，才点击预订。应复用已经命中的页面与行。
3. **定时逻辑存在可复现错误**：预热后立即刷新，而不是到规定时间；有查询结果就把未来开售时刻改成“现在”。这既不能保证到点准确执行，也可能提早耗尽 15 分钟窗口。
4. **存在比速度更优先的正确性问题**：停止后仍可提交已准备的订单；修改配置后旧订单意图仍可提交；整页关键词可能把帮助文字判为订单成功；删除未决记录会释放重复下单保护。

本次只新增审查文档和离线复现材料，没有修改生产业务代码，没有读取或导出生产会话，没有执行真实登录、抢票、候补或支付。

配套材料：

- `scripts/audit_regressions.py`：可重复运行的离线审查探针。
- `docs/audit-2026-09-20-results.json`：本次探针结果，共 15 个已复现问题和 1 条通过的 CLI 冒烟流程。
- `docs/audit-2026-09-20-manifest.json`：本次审查的 62 个源码、测试及依赖配置文件 SHA-256，便于修复前确认代码基线。
- 现有 `tests/`：135 项测试，本次在系统 Python 3.14.7 下全部通过。

## 4. 代码审查确认的其他问题

以下有代码路径证据，但本次没有运行真实浏览器来测量线上表现。不要把推断出的线上频率和耗时写成已测量数据。

### F01：会话被主动丢弃、浏览器每个操作重建（P1）

位置：`ui/worker.py:109` 的 RushWorker、`ui/main_window.py` 各 `create_application`、`bootstrap.py`。

GUI 登录完成后保存 session.bin，但关闭其浏览器。抢票创建新的 BrowserSession，传 `remember=False`。独立 `scripts/run_rush.py` 则使用 True，同一产品的两个入口行为不一致。“会话一定与浏览器进程绑定”只是代码注释中的假设，本次未验证，不能作为永久禁用会话恢复的理由。

此外 `BrowserSession.close` 不保存更新后的会话；抢票内重新登录成功后也没有统一保存动作。只改一个 remember 参数可减少部分重登，但不能解决每个操作重新建浏览器的架构问题。

### F02：登录识别把不确定状态当作已登录或未登录（P1）

位置：`session.py:141` 的后台探测、`:162` 的 `session_status`，`adapter.py` 的 `check_booking_login`。

账户页没有“请登录”且未跳转时即可返回 AUTHENTICATED，即使 account_ref 为 None。网络异常一律变成 LOGGED_OUT 或 False，又可能引发多余扫码。另一方面，check_booking_login 为 False 在订单预检中仅警告，继续下单。需要明确“已登录、确定失效、核验中、网络未知、账号未知”，不能把布尔值在各处解释成不同含义。

### F03：命中后丢失当前页面，重复导航（P1）

路径：`RushService.run` → `BookingService.precheck_and_prepare:77` → `BrowserSession.session_status:166` → `BrowserRailwayAdapter.prepare_order:223`。

命中后会离开预热结果页，访问账户页并执行 `wait_for_timeout(2500)`，接着又完整加载查询页和等待结果。这里能确认有固定等待及两次额外导航，不能确认真实总耗时。优化目标应是删掉这条重复路径，而不是跳过订单核验或更频繁地刷新官网。

### F04：抢票路径独立于限频/退避，时间预算不可靠（P1）

RushService 直接调用 refresh_results/read_hit，没有复用 QueryScheduler、CooldownGate、CircuitBreaker。真实 query_tickets 将各种加载异常统一转 TransientQueryError，没有将页面限流/身份核验明确分类。普通路径的冷却测试不能证明抢票路径具有同样保护。

`RushService.sleep` 默认是空函数；调用方忘传 sleep 时会忙等。统一注入 Clock 和取消信号，生产默认必须是真实可中断等待，测试再用虚拟时钟。

### F05：抢票只处理第一日期与第一席别，车次优先级不生效（P1）

`rush_service.py:128/:168` 固定读取 `dates[0]` 和 `seat_priority[0]`；JS 观察器按页面 DOM 行顺序选第一个命中，而非配置车次优先顺序。表单允许多值却静默忽略，应立即限制抢票模式只支持一个日期，再实现全部席别和车次排序。后续多日期由同一出行目标下多个子计划实现，不能分别无约束下单。

### F06：观察器结果过期与目标身份不完整（P1）

`left_ticket.py:151` 使用 `window.__ra_hit || null`，命中后不重新核验；重新安装也保留旧命中。观察器绑定原 tbody，替换 tbody 后未重新绑定；读取时主动扫描能部分补偿，但已置位的旧命中会持续返回。只返回车次字符串，无法证明日期、查询代次、区间、席别、页面身份仍匹配。

修复需使用结构化 CandidateHandle，按 query_generation 重置命中，检测 tbody 替换并重新绑定。不要在旧页通过长久保存的 ElementHandle 直接点击。

### F07：模拟与真实数据缺少强隔离（P0）

`TaskConfig.validate` 只接受 adapter=mock，但执行器可通过参数运行 browser。数据库 task/attempt 没有可信的 environment 隔离列，`recover_pending` 遍历全部活动尝试，可能使用 mock 核对真实尝试。真实授权记录也未绑定可验证的 account_ref；账号缺失时 idempotency_key 回退 anon。

任务配置中的 mock 目前不能作为“永远不会真实提交”的保证。修复后必须拒绝跨环境执行和恢复，账号切换使原预检失效。

### F08：购票目标范围和事务不完整（P0）

goal_id 当前为“出发>到达@日期”，既可能阻塞不同乘客的独立需求，又无法使同一出行目标的多个备选日期互斥。预检先迁移任务 BOOKING，再创建尝试，两步不在同一个原子事务中，数据库冲突/故障会留下无尝试的 BOOKING。

修复为显式用户出行目标 purchase_goal_id，并将环境、账号、目标锁、任务变更、attempt 和事件一起事务提交；跨日期备选共享同一目标。独立同行群体明确建立独立目标，同时做官方行程冲突预检。

### F09：成功、排队、支付状态混淆，浏览器过早关闭（P0/P1）

`main_window.py:538` 把 QUEUED 和 PENDING_PAYMENT 都称“抢票成功”，且固定提示 30 分钟。RushWorker 返回后上下文立即关闭；“打开官方订单页”使用 `webbrowser.open`，新默认浏览器不共享 Playwright 登录，可能再次要求扫码。

应分别显示排队中/待支付/已出票；读取官方实际支付截止，未知则显示以官方为准。保持同一账号上下文的官方支付/订单窗口供用户操作，完成或用户主动关闭后再回收；不自动付款。

### F10：后台停止和 GUI 退出不完整（P1）

GUI 多处在主线程 `wait(30000)`，造成最多 30 秒卡顿。登录等待最长 600/900 秒，没有 should_stop 检查；关闭窗口只处理 monitor/rush，未覆盖全部 JobThread。TaskService 的睡眠即使提前返回，下一行仍可能查询/下单；只有“可中断 sleep”不等于可取消业务。

停止任务时 monitor 分支可能只停 worker，没有持久化 STOPPED。需要把“发停止请求、引擎收到请求、停止新动作、未决订单继续核对、任务状态落库”区分为可观察的状态。

### F11：恢复、提醒与通知组件没有形成常驻闭环（P1）

RushService 保存 outbox 引用但不投递；RushWorker 改了 `app.tasks.notifier`，抢票实际不调用 TaskService 投递。MonitorWorker 没有周期调用 sale_times.check，也没有周期核对 BOOKING 订单；任务没有可查询项就退出，可能留下未投递通知和待核对订单。

`SaleTimeService.check` 检查的 summary base key 与实际 T10/T1/T0 事件 ID 格式不一致，即使阶段提醒发生过也可能在事后提示“提醒未送达”。要分别记录“已入队/已投递/未知”，不能仅凭不匹配的事件键得出未送达。

### F12：通知变化驱动下单，失败后可能一直不再尝试（P1）

`task_service.py:184` 仅当 matches_key 变化时调用 `_maybe_auto_submit`。如果第一次因缺授权或登录失败而未提交，用户修正后余票没变，则不会再次尝试；这不属于合法幂等保护。

将“通知是否去重”与“当前是否具备执行资格”解耦。明确拒绝、未发送的准备失败和提交结果未知必须走不同的后续策略，只有确认未创建订单的情况才允许重新评估，不能简单每轮重新 submit。

### F13：确认页核验仍有空缺（P0/P1）

`order_page.py:161` 用 select.inner_text 判断当前票种，这拿到全部选项而非当前选中项。student_ticket=False 时适配器保留官方默认票种，不能保证购买的是成人票。乘客仅按姓名匹配，遇同名无法证明身份。`PreparedOrder.valid_until/page_ref` 未在真实 submit_order 中验证。提交按钮点击异常会循环重试三次，必须明确异常发生在请求发送前还是之后；不能假设点击超时必然未发送。

修复：读取 selectedOptions/value，确认成人/学生票种；使用账号内稳定乘客标识和脱敏证件尾号区分，不保存完整证件；提交前核对全部已选票行、金额、票种与席别。无座权限应从 seat==无座派生，不能依赖目前默认 False 的 intent.allow_no_seat。所有可能已经发出的最终提交只允许进入核对，禁止自动重放。

### F14：通知 PowerShell 字符串构造和诊断不足（P1/P2）

`infrastructure/notifications.py` 将 json.dumps 字符串直接拼成 PowerShell 代码。JSON 转义不等于 PowerShell 转义，中文可能变成字面量转义，包含 `$()`、反引号或引号的消息可能被解释为代码。用 UTF-8 JSON 的 Base64 数据参数传递，在固定脚本中解码解析，或使用不经过 shell 代码插值的通知接口。加入包含这些字符的离线构造测试，不执行测试载荷。

日志白名单只保存时间、event、task_id，缺少 account/environment/session/query_generation/attempt_id/耗时，无法定位重复扫码或慢在哪一步。扩展白名单仅存脱敏标识和数值，不能直接记录整页正文、Cookie 或验证码。

### F15：运行环境与文档漂移（P2）

损坏的 venv 使启动器只检查 pythonw.exe 文件存在仍会静默失败。requirements.lock 含开发机器绝对 `-e` 路径，安装命令也没有实际使用 lock。README 同时声明“不会真实下单”和“真实下单已实现”，测试数、数据库版本、GUI 能力与当前代码不一致。

建立环境健康检查、可迁移锁文件、统一能力状态，启动失败写明确日志并展示错误。不能为了让测试通过去覆盖现有生产数据库或删除 session.bin。

## 5. 登录保持的完整修复设计

### 5.1 统一浏览器所有权

新增 `application/engine_service.py`、`application/session_service.py`，将 GUI 的短期 JobThread/独立 RushWorker 改为向一个长期 EngineWorker 发送命令。EngineWorker 独占浏览器、SQLite 写入和账号预算，所有 Playwright 操作在同一线程完成。

```text
GUI/CLI命令入口 → EngineCommandQueue
                       ↓
                 长期 EngineWorker
                  ├─ SessionService → 一个 BrowserContext
                  │                    ├─ 工作查询/确认页
                  │                    ├─ 登录或身份验证页
                  │                    └─ 订单/支付页
                  ├─ 查询/起售/订单调度
                  ├─ BookingService + RecoveryService
                  └─ OutboxDispatcher
```

不能同时把同步 Playwright 对象交给多个 Qt 线程。CLI 单次命令可保持独立进程行为，但如果 GUI 引擎已占有数据目录，应清楚提示通过 GUI 操作；本轮不要求额外实现 IPC。CLI 连续抢票应复用同一个长期引擎，不能每一步重启。

### 5.2 SessionService 行为约定

新增状态：`RESTORING / AUTHENTICATED / EXPIRED / VERIFICATION_REQUIRED / UNKNOWN / LOGGED_OUT`。返回 `SessionHealth(state, account_ref, checked_at, reason_code, generation)`。

1. 第一次使用才启动 browser；同次软件运行的登录、查询、抢票、核对、付款始终共享 context。
2. 用户启用“记住登录”后尝试加载 DPAPI 快照；载入成功只表示数据可解密，不能直接认定已登录。
3. 优先用当前页面明确的已登录标记与账号身份确认；必要时使用同 context 独立检查页，禁止导航离开抢票工作页。
4. 超时/网络失败返回 UNKNOWN，保留现有会话并通知检查；只有明确失效才要求重新登录，核验状态单独提示。
5. 登录成功、可信会话更新、正常退出时进行受控原子保存；异常/登出页的空数据不得覆盖上一次有效快照。首次登录后立即保存，不能只依赖退出保存。
6. 用户明确退出：取消新购票动作，关闭工作页/销毁 context，清除本地快照，界面显示“本地登录已退出”；如果需要官方登出，单独走已验证的官方流程。离线清除本地会话不应要求启动浏览器。
7. 账号变更时更新 generation，清理页面候选，原授权失效；未决订单保留原账号归属并提示切回原账号核对。
8. 将现有 checkUser 接口视为待验证的观测手段，不把定期调用描述成“必然续期”。错误分类、超时和频率都由统一 SessionService 管理。

Playwright 官方文档支持恢复浏览器认证状态，但是否足以恢复某站点登录取决于其认证模型；sessionStorage 也不是默认 storage_state 自动持久化的内容。应先测出缺失状态，再决定是否需要特定域的附加保存，不能无差别导出所有存储。[Playwright 身份验证文档](https://playwright.dev/python/docs/auth)

官方登录仍可能要求 App 或其他身份核验。因此目标是“消除本程序造成的重复扫码，官方会话仍有效时复用”，不是承诺永不扫码或固定保持 1—2 小时。[12306 官方登录页](https://kyfw.12306.cn/otn/resources/login.html)

### 5.3 登录专项验收

- 同次 GUI 运行：登录→查看任务→准备抢票→到点→订单核对，不新建第二个 context，不主动重新打开扫码页。
- 重启：有效快照恢复后，明确登录标记成立才免扫码；过期快照提示一次登录。
- 网络暂时断开：显示未知而不是确定失效，不清空快照、不连续弹扫码。
- 登录后取消等待：取消响应在 1 秒内到达 UI；正在进行的浏览器操作在明确超时边界收敛，不再启动下一步。
- 支付页使用同一 context，用户切换浏览器需要单独提示会话不共享。
- 新增 tests/unit/test_session_service.py 和本地页面测试；真实长时间保持登录另做人工只读验收，不写死线上过期时长。

## 6. “提前打开，08:15 到点执行”的完整修复设计

### 6.1 明确日期语义

用户例子按“已核实的乘车日 2026-10-05、开售时刻为明天 08:15”建模。在本次日期上下文中，明天是 `2026-09-21T08:15:00+08:00`。这只是说明配置关系，本文没有核实该实际列车的售票安排。

```json
{
  "travel_date": "2026-10-05",
  "sale_at": "2026-09-21T08:15:00+08:00",
  "sale_source": "manual_confirmed",
  "sale_verified_at": "2026-09-20T20:00:00+08:00",
  "warmup_lead_seconds": 300,
  "execution_mode": "scheduled",
  "auto_submit": true
}
```

这是目标模型示例，不是当前 TaskConfig 可直接导入的配置。GUI 同屏显示乘车日期、开售日期、时区和倒计时，避免填错。官方起售页面也提示时刻可能调整，不能用一个固定预售天数推算替代已确认的具体开售时间。[官方起售查询](https://www.12306.cn/index/view/infos/sale_time.html)

显式指定未来 sale_at 时始终遵守它。“立即捡漏”必须是另一个用户可见的执行模式；不能因为 query_tickets 成功就暗中切换模式。站点起售规则只提供时分、有效范围时，结果标记为规则信息，尚不足以生成精确 sale_at；缺少销售日期或预售规则证据时要求补充日期。

### 6.2 精确运行阶段

| 时刻 | 阶段 | 应做的事 |
| --- | --- | --- |
| 用户启动计划 | VALIDATING | 检查自动提交开关、配置、账号、授权期限、能力、乘客数和未决订单；不等到开售才发现缺授权 |
| T-10 分钟或立即 | WAITING/WARMING | 若已失效，尽早让用户完成核验；读取目标站码等静态信息 |
| T-5 分钟（08:10） | WARMING | 打开目标查询页面，设置区间和乘车日，确认工作页身份；无车次也可完成预热 |
| T-1 分钟（08:14） | ARMED | 最后一次预检，冻结配置 revision；准备选择器与观察器；停止非必要后台业务占用关键页和预算 |
| T（08:15:00） | QUERYING | 在允许预算内触发一次官方页面查询；T 之前不执行定时购票提交 |
| 结果显示可预订 | CANDIDATE_READY | 对当前查询代次结果匹配车次、日期、区间、席别和人数，立即获取目标锁 |
| 官方预订入口可用 | PREPARING | 使用同一工作页点击当前候选进入确认页；选择并核验乘客/票种/席别/金额 |
| 官方确认按钮就绪 | SUBMITTING | 重新做本地授权及取消校验，持久化提交边界，执行一次官方确认 |
| 提交返回 | QUEUED / PENDING_PAYMENT / OUTCOME_UNKNOWN | 继续同账号核对；付款入口留给用户，不能宣布已出票 |

如果开售前官方不允许进入确认订单页，提前可打开的是查询/购票入口页，而不是已经锁定车票的确认页。不能承诺在开售前预生成订单、绕过按钮倒计时或核验。

### 6.3 时钟与调度伪代码

```python
# 伪代码：需按下面接口与状态机实现，不能直接替换成无保护的 sleep 循环。
sale_wall = plan.confirmed_sale_at
deadline = clock.monotonic() + (sale_wall - clock.wall_now()).total_seconds()
await_or_wait_until(deadline - warmup_lead, cancel)
warm_query_page(plan)                 # 不强求已有可购买结果
preflight = validate_current_context(plan)
set_state(ARMED)
await_or_wait_until(deadline, cancel)
budget.acquire_or_defer("sale_query", priority="scheduled")
generation = refresh_query_once(plan)
candidate = wait_for_current_candidate(generation, cancel, query_timeout)
if candidate is not None:
    booking.execute_from_current_page(plan, candidate, preflight, cancel)
```

修复 R01 的最小计算是 `poll_start = sale_at - timedelta(seconds=...)`，不能用 min(sale_at, now)。但目标方案不需要 T-30 秒就高频访问官网；T-30 可只做本地就绪检查，到 T 才发查询。所有“提前量”要区分页面预热和网络查询，不再混用。

使用 monotonic 控制短等待和计时，wall clock 解释用户日期；检测休眠唤醒和显著系统时间跳变后重新计算 deadline并记录原因。恢复晚于 T 时最多立即进行一次允许的查询，不回放积压轮次；晚于任务截止即过期。

### 6.4 命中后走当前页面

新增接口：

```python
warm_query_page(query) -> QueryPageToken
refresh_query(page_token) -> QueryGeneration
find_candidate(page_token, generation, selection) -> CandidateHandle | None
prepare_order_from_candidate(intent, candidate, preflight) -> PreparedOrder
submit_prepared(prepared, cancel_token) -> SubmissionResult
```

CandidateHandle 至少含 context_id、page_id、account_ref、task_revision、query_key、query_generation、travel_date、区间代码、train_code、seat、observed_at_monotonic、行的可重定位标识。它不是供跨进程持久化或重放的网页句柄。

`prepare_order_from_candidate` 应先核验 token、当前页面查询参数和目标行，然后直接预订；不得调用会离开当前页面的 session_status，不得默认 page.goto 查询页。页面已经改变时返回 `STALE_CANDIDATE` 并经过预算重新采集，不能使用旧命中。

保留现有通用 `prepare_order` 供人工点击“提交一次”的路径使用，但两者必须汇合到同一个确认页核验和最终提交协调器，不能出现一套快速路径跳过授权或订单锁。

### 6.5 性能目标及测量

以下是修复后在受控本地页面、电脑清醒、无验证码、无 CPU 饱和时的目标，不是对真实出票时间的保证：

- 本地定时器 T→开始发起查询：P95 ≤200 ms；连续测 100 次，记录 P50/P95/最大值。
- 当前 DOM 可预订→本地决定并尝试点击：P95 ≤300 ms；不得插入账户页导航和 2.5 秒固定等待。
- 命中→预订前额外整页导航次数：0；同次运行的新建 BrowserContext 次数：1。
- 配置/账号/预算/授权越界：0 次真实提交；结果不明时自动重复提交：0 次。

端到端时间分段记录：本地触发延迟、官方查询响应、页面渲染、候选检测、确认页加载、乘客及金额核验、官方按钮等待、最终返回。不把服务端排队、风控核验、按钮倒计时混为本地慢，也不承诺“毫秒出票”。

### 6.6 统一请求控制

优先通过消除冗余导航和准确到点获得速度。现有“2 秒以下必触发风控”“每 10 分钟一定续期”等陈述没有本轮官方证据，应从文档和代码注释删去绝对结论。

普通查询、定时查询、登录探测、订单核对经过同一个账号 RequestBudget。T 前预留一次查询许可并停止低优先级业务，预算未允许时清楚显示预计执行时间；用户停止或遇核验后不继续消耗许可。开售点没有命中时按已验证的页面允许节奏调度，不通过多进程、多账号或重复整页刷新增加并发。

请求适配器将限流、核验、维护、网络失败、结构变化和未开售分别归类。Retry-After 大于本地 30 分钟时必须等待服务端要求的更长时间。DOM 本地扫描频率与服务器查询频率分别配置，150 ms 本地检查不意味着每 150 ms 发查询。

## 7. 订单可靠性修复规格

### 7.1 最终提交前必须重新验证

实现 `SubmissionGuard.validate_current(attempt, prepared, cancel)`，在最后可能创建/确认订单的动作前校验：

- environment 与当前 adapter 一致，account_ref 非空且一致，session generation 未变。
- 当前任务不是 PAUSED/STOPPED/EXPIRED；尚未超过 stop_at；自动模式仍开启 auto_submit。
- 当前任务 revision、授权 revision、intent revision 三者一致；授权未过期。
- 实际选择的日期、区间、车次、票种、席别、乘车人身份及人数均在授权范围内。
- 金额为有效正整数分，适用普通金额或候补预付款上限；无座/新增列车授权单独核验。
- PreparedOrder 未过期；对应 context/page/query generation 和摘要仍有效。
- 当前目标锁归本 attempt，且没有任何同目标未知/待支付/有效候补订单。

取消标志须在获取候选、进入确认页、点击首个提交按钮、点击最终确认按钮之前检查；一旦请求可能已经发出，取消只能停止后续新下单，不能把远端结果判成未提交。

### 7.2 结构化订单核对

废弃“整页任意出现已支付就成功”。新增 OrderPageParser，输出 `OfficialOrderSnapshot`，包含订单标识、账号归属、乘车日、车次、区间、乘车人集合、席别、状态及支付截止。

优先按 remote_order_ref 精确查找；没有订单号时，按完整业务指纹和尝试时间范围匹配。多个候选或字段不足时为 UNKNOWN，保留锁并请求人工核对。只有匹配到本次目标且状态明确才更新本地订单。不能只查未完成列表就确认已完成、取消或不存在；需要完成订单页面的已验证只读路径，缺失则能力不可标为完整 reconcile。

固定帮助文字、别的订单、历史订单、空列表、跳到登录页、仅包含“请在”等提示都必须在离线 fixture 中覆盖。QUEUED 不代表成功，PENDING_PAYMENT 不代表出票。

### 7.3 订单锁、删除与恢复

活动 attempt 禁止物理删除。改为“隐藏记录”或 `archived_at`，隐藏不释放锁。只有官方确认终态或能够证明尚未发送的 PREPARING 失败，才允许结束尝试并释放锁；未知状态不能因为本地点击放弃而变成 CANCELLED。

将 PREPARING 与 SUBMITTING 分开，记录“已开始可能产生副作用动作”的边界。对所有无法证明无副作用的崩溃/超时保持未知并核对；不因为名称为 prepare 就假设其中的页面操作没有副作用。

Engine 持续处理待核对订单，独立于是否还有查询任务。核对退避持久化，重启先恢复原环境、账号和未决尝试，绝不使用 mock 给 browser 尝试生成结果。READY 任务直接下单也要进入正确任务状态；订单成功后即使任务已停止，订单记录仍应正确更新，界面表达为“任务已停止，既有订单已出票”。

## 11. 修复完成的定义

只有满足以下条件才能向用户说明“已修复重复扫码和开售响应慢”：

1. 有效官方会话在同次运行内被复用；官方过期会明确提示，不能用虚假“保活成功”掩盖失效。
2. 配置具体日期的 08:15 后，到点执行行为有可核验时间线，提前打开页面没有被后续登录检查破坏。
3. 命中到预订的本地路径满足性能目标，服务端耗时单独展示；没有靠放宽订单核验或绕过官方等待来达成指标。
4. 订单匹配、最终授权、取消和重复保护通过负面测试；模糊结果不误报成功。
5. 修复者提供改动文件、测试结果、性能样本、数据迁移结果和真实能力的已知限制。

本文给出的修复接口和性能目标是实施约定，尚未写入业务代码；本次已经执行和可重复验证的证据以第 2—3 节及配套 JSON 为准。
