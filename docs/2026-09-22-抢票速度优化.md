# 抢票流程与速度优化（2026-09-22）

目标：提高定点起售抢票的成功概率——命中要早、下单要快。

## 改动

### 1. 命中瞬间不再重复发网络校验（省 0.3~1 秒）
`application/booking_service.py` · `precheck_and_prepare`

命中后原本会连发**两次** `checkUser` 网络请求：
- `current_session_status()` 内部一次（用于确认会话）；
- 紧随其后的"软提示"分支又一次。

抢票路径（`session_prevalidated=True`）已经在同一浏览器上下文校验过，第二次纯属重复。
现在 `session_prevalidated=True` 时跳过软提示那次校验，**只保留必要的会话确认**。

### 2. 命中读取粒度 150ms → 50ms
`application/rush_service.py` · 新增 `HIT_READ_INTERVAL = 0.05`

页面内观察器（MutationObserver）在官方结果表刷新的一瞬间就把命中标记置位，
真正的延迟只取决于我们多久去读一次。150ms → 50ms 把**平均发现延迟从 ~75ms 降到 ~25ms**。

### 3. 轮询间隔设到安全下限 2 秒
配置项 `rush_interval_seconds = 2`（README 明确 2 秒是下限；再快会触发 12306 风控，反而毁掉窗口）。

### 4. 新增下单耗时日志（可量化瓶颈）
`application/rush_service.py`

命中后打印三段耗时：
```
下单耗时：预检 X.XXs，确认页+提交 Y.YYs，命中到结果合计 Z.ZZs
```
用于下次真实命中时定位瓶颈（预检多为本地 + 一次会话校验；确认页+提交受官方倒计时按钮影响）。

### 5. 文案修正
等待预热窗口的提示原先写死"每 10 分钟自动保活"，实际已改为 5 分钟；现按 `KEEPALIVE_INTERVAL` 动态显示。

## 未改动（有意保留）

- 预热阶段仍走完整导航 + 安装观察器，**不在开售前刷新**（避免无谓请求与风控）。
- 首次刷新严格对齐开售时刻（2026-09-21 实测误差 < 1ms）。
- `prepare_order_from_current_page`（复用当前结果页，不做二次导航）保持不变。

## 配套发现

- 官方**起售时间是车站固定属性**（北京南 12:45 / 南京 08:15 / 上海虹桥 13:45），
  规则有效期 2010-01-01 ~ 2099-12-31；`sale-time fetch` 恒返回 null 属过度保守，建议改为直接返回 HH:MM。
- 结果页席别格 **`*` = 未到起售时间**；未开售日期的页面**仍会渲染车次行**，
  因此 `_probe_queryable()` 的"有行即已开售"启发式不成立（仅影响未配置 sale_at 的路径）。
