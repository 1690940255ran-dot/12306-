# 诚实评估：速度够不够、保活够不够（2026-09-24）

> **已由真机实测更新**：本文原写"直达省 2~5 秒（未验证）"。21:45 的真机结果把它推翻了——
> 官方"预订"是 POST 表单 + 服务端会话上下文，GET 直达会被回"系统忙"，`order_fastpath` 已默认关闭。
> 真实可用路径（重新导航 + 点预订）实测 **1.4~5.2 秒**。
> 请看 `docs/2026-09-24-真机验证-直达路径不成立.md`；本文保留当时的评估框架与保活长测设计。

问题（用户原话）：**"你确定速度够了，保活时间够了？"**

直接回答：

- **速度：不够。** 对"1 秒售罄"的热门车次，本工具**抢不到**这个结论没有改变。
  这次只是把**我们自己白交的时间**拿回来（约 3~6 秒），动不了官方页面加载的地板。
- **保活：有条件够。** "提前一小时打开→到点不用扫码"这一条基本解决；
  但"挂机越久下单越可能被拒"的规律**仍未被排除**，若真因是下单资格独立过期，
  **保活救不了**。

下面是"我验证了什么 / 没验证什么"（不粉饰）。

## 二、速度：能省的与省不掉的

```
命中(T) ──▶ ① 进确认页 ──▶ ② 填写 + 官方提交 ──▶ 结果
             ↑ 这次优化在这里
```

- **这次省掉**：① 里的**第二次整页加载**（旧实现：重新导航结果页 → 再点"预订"），
  实测历史值 **7.86s / 7.77s（全新导航） vs 2.39s（复用页面）**，差值约 **5 秒**；
  再加上自己那 ~1 秒固定等待。**合计约 3~6 秒**——但这是**推算**：
  前提是"直达 URL 被官方接受"，而这一点**没在真实站点验证过**。
- **省不掉的**：官方确认页自身加载、官方"提交订单"弹窗的灰→橙倒计时。
  即使一切顺利，**仍是秒级**。
- **因此**：热门车次请不要指望本工具硬抢。**官方候补**才是那类票的正解
  （本工具目前**没有**自动候补；要不要做，你说了算）。

## 三、保活：够的条件与不够的情形

**够**（这些条件下，挂机一小时不用再扫码）：

- 电脑不睡眠、网络不断；
- **不在手机/别处登录同一账号**（会把网页端踢下线）；
- 官方没触发风险核验（短信/人脸/滑块）；
- 保活进程活着（GUI 登录后自动开始；CLI 用 `keepalive`）。

**不够**（保活也无能为力）：

- **"下单资格"独立过期**：早前五次现场数据显示——会话年龄 ≥100 分钟、checkUser
  一直报有效，但确认页打不开。若这就是原因，那么"保活到 1 小时后能下单"是**假的**，
  唯一解法是**开抢前 20~30 分钟再扫码**。
- 官方强制下线 / 风控核验 / 多设备登录：必须本人重新扫码。

**这次改动对这一条的作用**：把保活从"每 3 分钟发一次 checkUser"改成
"checkUser + 一次真实页面访问 + 重新落盘"。
- 若真因是"高频打卡被判脚本"→ 会缓解；
- 若真因是"资格寿命"→ **没有作用**。
**不隔离出真因就不宣称修复**——这句话我保持不变。

## 四、怎么把"不确定"变成"有数据"

新增只读探针 `scripts/probe_confirm_speed.py`：**只打开确认页，不点提交、不产生订单**。

### 问题 1：直达到底快不快（真实站点实测）

```powershell
.venv\Scripts\python.exe scripts\probe_confirm_speed.py `
    --from 南京 --to 江都 --date 2026-10-04 --train C436 --runs 3
```

输出：直达 / 重新导航+点击 两条路径的中位数、最小、最大，以及"本次直达省下多少 ms"。
结果写入 `docs/confirm-speed-<时间戳>.json`。

判读：
- 直达中位数明显小于点击、且 `ok` → **省下的秒数就是真的**；
- 直达全 FAIL（会回退）→ 说明官方拒绝了我们的 URL 形态，**这 5 秒没省下来**，
  我会按实测参数修正（探针会打印具体原因）。

### 问题 2：挂机久了还能不能下单（决定性实验）

```powershell
.venv\Scripts\python.exe scripts\probe_confirm_speed.py `
    --from 南京 --to 江都 --date 2026-10-04 --train C436 --warmup-minutes 70
```

先按 GUI 同款保活跑 70 分钟，再测确认页：
- **能打开** → 保活保住的是"可下单"，你"提前一小时打开"的用法成立；
- **打不开** → 证明下单资格会独立过期，**必须改成"开抢前 20~30 分钟扫码"**，
  我会把这条写死在 README 与 GUI 提示里，不再让你白等。

> 探针会占用数据目录实例锁：跑之前请关掉正在进行的抢票/监控。

## 五、结论（一句话版）

- **速度**：优化是真的（省掉白交的 3~6 秒），但**对 1 秒售罄的票仍然不够**，
  且这 3~6 秒在真实站点**尚未被证实**。要用数据说话，就跑上面第一条命令。
- **保活**：**"不用重复扫码"基本够了**；**"挂机一小时还能下单"尚不确定**，
  跑上面第二条命令就能定论。
- 两者都不改变这条底线：**热门车次优先官方候补**；本工具定位是"定点帮你把下单动作做完"，
  不是"保证抢到票"。
