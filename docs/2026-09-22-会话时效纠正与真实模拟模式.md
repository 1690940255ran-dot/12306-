# 会话时效纠正 + 定点抢票修复 + "真实模拟"模式

日期：2026-09-22

## 一、先纠正我昨天的一个错误表述

我昨天说"无保活约 **45 分钟**掉线"——**这个说法不准确**，向你说清楚。

重新核对两个现场数据点（都看**最后一次活动到掉线**的间隔，而不是"登录到掉线"的总时长）：

| 现场 | 最后一次活动仍有效 | 已确认失效 | 空闲间隔 |
| --- | --- | --- | --- |
| 昨天 | 11:25（保活 ping 返回有效） | 11:36 | **约 11 分钟** |
| 今天 | 12:35:22（保活 ping 返回有效） | 12:45 | **约 10 分钟** |

**结论：12306 网页会话的空闲存活时间约 10 分钟。** 我昨天把"10:49 登录 → 11:36 失效"这个总跨度
（其中 11:25 还有一次活动）当成了"会话寿命"，于是误报成 45 分钟。

**"保活能撑 4 个多小时"这句话本身没错**：昨天 60 次 ping、每 5 分钟一次、全程有效——
因为 **5 分钟 < 10 分钟的空闲窗口**，会话就被一直续着。两个观察其实是自洽的，
错的是我把"空闲窗口"讲成了"会话寿命"。

## 二、今天 12:45 为什么会掉线（真实缺陷）

抢票的保活在 **`warm_at`（12:40 预热）那一刻就退出了循环**：

```
12:35:22 登录保活正常      ← 最后一次续期
12:40:00 预热：打开官方查询结果页
12:45:00 开始轮询
12:45:01 命中 G1！开始下单
12:46:13 失败：点击预订后未到达确认订单页（会话已失效）
```

从 12:35:22 到 12:45 有 **10 分钟空档**，正好踩过 ~10 分钟的空闲窗口 → 开抢瞬间会话已死。

**更隐蔽的一点**：**查看余票不需要登录**。所以会话即使已经失效，
预热照样成功、不报错，直到 12:45 点"预订"才暴露——**那时已经来不及**。

## 三、修复（3 处）

| # | 改动 | 文件 |
| --- | --- | --- |
| 1 | 保活间隔 300s → **180s**（3 分钟），对 ~10 分钟空闲窗口留足余量 | `application/rush_service.py` |
| 2 | **预热完成后立刻校验一次下单登录**；失效则打开登录窗，等待上限按"距开售剩余时间 − 30s"计算 | 同上 |
| 3 | **预热后到开售之间继续保活**（不再停在 `warm_at`） | 同上 |

修好后，`12:35 → 12:45` 这种 10 分钟空档不会再出现。

## 四、新增"真实模拟"（演练）模式

你说不需要真抢票、只要真实模拟——所以加了这个模式：

```json
{ "rush_mode": true, "dry_run": true, ... }
```

**行为**：抢票命中后，**完整走完**官方确认页核对（车次 / 日期 / 区间 / 乘车人 / 票价）+
金额与授权复检，然后在点击"提交订单"**之前停止** → **绝不产生订单**。

- 订单尝试记为 `CANCELLED`（终态，不阻塞后续任务）；
- 结果是"真实"的：真实浏览器、真实 12306、真实余票、真实确认页、真实票价读取，只是不落单；
- `dry_run=true` 时**不再强制要求** `auto_submit=true`（避免"为了演练而打开自动下单"）。

代码位置：`application/booking_service.py` · `submit(attempt_id, dry_run=False)`，
演练分支位于**所有安全检查之后、唯一提交动作之前**。

## 七、顺带修掉一个"购票目标被锁死"的缺陷

**现象**：12:45 那次失败尝试停在 `NEEDS_USER_ACTION`（非终态），数据库按"同一购票目标互斥"
把 `北京南>上海虹桥@2026-10-06` 永久占住；而：

- `order cancel` 只允许取消 `PREPARED` → 拒绝；
- `order delete` 拒绝删除非终态记录 → 拒绝；
- 官方"未完成订单"页又读不出结论（恒 `UNKNOWN`）→ 走不通；

结果：**目标被锁死，无法重试**。报错还只说"幂等键重复"，完全没说要怎么办。

**修复**：

1. 新增 `SQLiteTaskRepository.attempt_may_have_created_order()`：
   只要**进入过 SUBMITTING 就保守处理**（设计上"先落库再动作"，所以不能凭它断定没发出）；
   只有**失败原因明确属于"从未触达官方提交动作"**才判定为安全可清理：
   `prepare_error:*`（确认页阶段就失败）/ `dry_run`（演练）/ `user_abandoned`。
2. `order cancel` 与 `delete_attempt` 据此放行（原先只有 `PREPARED` 能取消）。
3. 冲突报错改为**点名是哪条记录挡住了**，并提示可用 `order cancel` 清理。

**单测**：新增 2 项——`prepare_error` 的尝试可安全删除；无失败原因的 `SUBMITTING` 必须保守处理。
