# 抢票提速 + 保活修复（2026-09-24）

> **重要更正（2026-09-24 21:45，真机实测）**：本文第二节"命中瞬间直达确认页"的优化
> **经真机验证不成立**——官方"预订"是 **POST 表单 + 服务端会话上下文**
> （`POST /otn/confirmPassenger/initDc?N`，body 仅 `_json_att=`，URL 里没有车次参数），
> GET 拼参数直达会被回"系统忙，请稍后重试"（6/6 失败）。
> `order_fastpath` 已**默认关闭**。真机数据、实测耗时与结论见
> `docs/2026-09-24-真机验证-直达路径不成立.md`。
> 本文其余部分（保活改动、固定等待压缩、GUI 缺陷修复）仍然有效。

用户反馈两件事：

1. **速度不够快**：国庆的票几乎一秒没，现在的速度抢不到；
2. **保活时间不够**：提前一小时打开软件，等到抢票时又要重新扫码登录。

下面分别给出**根因**、**改了什么**、**还能快到什么程度**（不粉饰）。

---

## 一、保活：根因是"登录做完就没有东西在续期"

### 根因（代码级）

| 事实 | 位置 |
| --- | --- |
| 登录操作在**自己的线程里开浏览器、扫码、存会话，然后线程结束就关掉浏览器** | `ui/main_window.py:_login_action` → `worker.py:JobThread` |
| 抢票前的等待期间**没有任何进程持有会话** | 保活只存在于抢票进程内部（`rush_service._sleep_until(keepalive=True)`） |
| 12306 会话是**闲置滑动过期**：约 10 分钟无活动即失效 | `docs/2026-09-21-登录保活.md` |

于是"提前一小时打开 → 扫码 → 挂机 → 到点抢票"必然走到"会话早就过期，请重新扫码"。
这不是保活"时间不够长"，而是**等待期间根本没有保活**。

### 改动

1. **新增 GUI 保活线程** `ui/worker.py:SessionKeeperWorker`
   - 持有浏览器会话，每 **150 秒**续期一次（`KEEPALIVE` 默认 240 秒，GUI 更密），
     抢票内部是 180 秒；
   - 每轮做三件事：`checkUser` 续期 → **一次官方页面轻量访问**（结果页，
     只等 DOM 就绪、不解析表格）→ **重新加密落盘会话**（活动时 Cookie 会轮换）；
   - 抢票前**让位**：点"开始抢票"会先停掉保活线程（浏览器是单实例，两个 Chromium
     同时用一份会话会被官方判为异常登录）；
   - 抢票结束/任何一次性操作结束后**自动恢复**保活。
2. **打开软件即自动接上保活**：本地存在加密会话（说明上次扫码登录过）时，
   `MainWindow` 启动后就拉起保活线程——用户"提前一小时打开"这个动作本身就足以维持登录。
3. **保活间隔可配**：`KeepAliveService(visit_page=True)`，间隔下限 60 秒；
   "保活 = 只发 checkUser"这个假设也被改掉了：
   本次同时做**真实页面访问**，更接近"人开着页面在看票"，也降低"高频打卡被判定脚本"的风险。
4. **会话失效仍会明确报告**：保活线程发现 `checkUser` 返回未登录、
   或本地会话已失效时，会**结束并提示本人扫码**，不静默空转。
5. 顺带修掉一个会让"抢票任务改不了"的 GUI 缺陷（见第四节）。

### 结论

保活能覆盖"提前一小时打开、到点再抢"的用法；**唯一仍必须本人操作的是首次扫码**
（以及官方强制下线/风控核验）。会话活不过夜与"扫码必须本人"这两条边界没有变。

## 二、速度：先盯住真正的瓶颈

下单链路的耗时只有两段：

```
命中(T) ──▶ ① 进确认页 ──▶ ② 页面填写 + 提交 ──▶ 结果
```

历史上实测（2026-09-23）：**② 约 2.4 秒**（复用预热页面）/ **7.9 秒**（全新导航），
而 ① 在旧实现里等于**第二次整页加载结果页 + 点击"预订"**——那 2~5 秒纯粹是白交的。

### 2.1 命中瞬间直达确认页（省掉一次整页加载）

- 结果行"预订"按钮的 `onclick` 里带着**放票后新生成的 token**；
  旧实现只在命中后重新导航结果页、再去点它，等于把同一份数据取两次。
- 现在命中一瞬间就在同一次 DOM 扫描里把该行的 `onclick` 参数一并取出
  （`left_ticket._OBSERVER_JS` → `read_hit_detail`），拼成确认页 URL
  （`left_ticket.build_confirm_url`）后**直接导航到确认页**
  （`adapter.prepare_order_direct` → `order_page.open_direct`）。
- **这不违反"不能复用预热页面"的结论**（2026-09-23）：用的不是放票前加载的旧页面，
  而是**命中那一刻的新 token**，与官方按钮自身的跳转目标一致。
- **失败一定回退**：token 结构不符 / 导航没落到确认页 → 自动走回
  "重新导航 + 点预订"，且回退原因写进订单尝试的核对摘要
  （`direct_navigation_error`）。只有"直达这一步没走通"才回退；
  会话失效、乘车人/席别不符等错误原样上报，绝不靠再导航掩盖。
- 开关：任务配置 `order_fastpath`（默认开；任务编辑对话框可关，用于回滚）。

### 2.2 压缩我们自己的固定等待

| 位置 | 原 | 现 |
| --- | --- | --- |
| 确认页乘客区就绪 | 由"固定等页面渲染完"隐式承担 | `wait_passenger_row`：按元素就绪轮询（50ms 粒度，最多 3 秒） |
| 票种切换后等待 | 300ms | 120ms |
| 席别切换后等待 | 300ms | 120ms |
| 弹窗关闭后等待 | 800ms | 300ms（下一轮仍会确认弹窗真的消失） |
| 提交后结果轮询 | 400ms | 150ms |
| 确认页就绪判定 | 最多等 20 秒 | 直达路径最多 6 秒（失败即回退，不空等） |

### 2.3 命中读取仍保持 50ms 粒度

`HIT_READ_INTERVAL = 0.05` 未改：页面内 `MutationObserver` 在官方渲染瞬间置位，
平均发现延迟约 25ms。

### 2.4 预期收益（诚实版）

- **能省的**：确认页那一步的第二次整页加载 ≈ **2~5 秒**，加上自己那 1.5~2.3 秒里的
  约 **1 秒**固定等待 → 单次尝试合计约 **3~6 秒**。
- **省不掉的**：12306 自身的确认页加载、官方提交弹窗倒计时（点击"提交"后
  官方自己的 `qr_submit_id` 会先灰后橙）。
- **对"一秒售罄"的热门车次**：浏览器方案仍然抢不过直连接口/官方候补。
  真正提高成功率的顺序仍是：**① 官方候补** → ② 错峰/冷门车次 →
  ③ 本工具定点抢（现在比之前快 3~6 秒）。
- 这次优化**没有**改变安全边界：不直连接口、不猜测点击、不重复提交，
  确认页上的车次/日期/区间/乘车人/票价仍然逐项核对。

## 四、顺带修复：带"开售时间"的任务在 GUI 里改不了

`ui/task_editor.py` 原先用 `QDateTime.fromISOFormat(...)` 回填时间，
而本机 PySide6 **没有这个类方法** → 编辑任何带 `sale_at`/`start_at`/`stop_at`
的任务时对话框直接抛 `AttributeError`（任务改不了、也复制不了）。
现改用 `QDateTime.fromString(..., Qt.DateFormat.ISODateWithMs)` 并转本地时区，
回填/保存往返一致（已有单测覆盖）。

## 五、仍未做 / 需要现场复验的

- **确认页直达的 URL 形态尚未在真实 12306 上跑通一次**：参数取自
  "预订"按钮 `onclick` 的原始结构，拼出的查询串为
  `train_no`（官方内部编号）/ `station_train_code` + `stationTrainCode`（显示车次号，
  两种写法都带上）/ `fromStationTelecode` / `toStationTelecode` / `leftTicket`（token）/
  `purpose_codes=00`。若官方另有隐藏校验，表现是"直达失败 → 自动回退"，
  日志会记 `direct_navigation_error`，**不会导致抢不到票**。
  下次真实命中时请看这两条日志：
  - `确认页直达失败（…），已回退到重新导航下单。`（回退发生了）
  - 下单耗时里的"预检 X.XXs"（直达成功时应明显小于旧的 5~8 秒）。
- **回退分支已被 mock 真实覆盖**：`MockRailwayAdapter.fail_direct_url=True` 会抛出与
  浏览器适配器同款文案（"未到达确认订单页"），因此测的是 booking 侧的真实回退判据，
  而不是一条自定义文案绕过去。
- **"挂机越久越难下单"（会话新鲜度）**：`docs/2026-09-23-会话新鲜度决定下单成败.md`
  的两个假设仍未隔离。本次把保活改成"checkUser + 真实页面访问 + 重新落盘"，
  如果真因是"高频 checkUser 被判定脚本"，这次改动会顺带缓解；
  如果真因是"下单资格本身约 1 小时寿命"，则唯一解法仍是**尽量晚扫码**。
  **需要一次对照实测才能定论**（见该文档§四实验设计）。
- 真实候补提交仍未实现（官方候补请用手机 App，成功率更高）。
