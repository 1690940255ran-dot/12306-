### 已知限制（现场发现）

- 账户页昵称选择器未命中，`account_ref` 为空（登录态判断不受影响，仅影响脱敏标识显示）。

- 表头/接口结构变化会触发能力熔断（解析为空或表头不符时返回错误而非猜测数据）。

### 实现的门控顺序

1. `order unlock --confirm`（本机显式解锁 submit_order/reconcile 能力）
2. `order authorize --confirm`（授权快照：乘车人、金额上限、候选范围、任务配置哈希）
3. 登录有效（官方账户页判定）+ 能力已验证
4. 提交：预检 → 确认页核对（车次/日期/区间/乘车人不符即转人工）→ 页面金额复检上限 → 先落库 SUBMITTING → 单次提交 → 结果分类 → outbox 通知支付

### K4（2026-09-19 现场验收通过）：真实购票

真实运行记录：预检（登录/授权）→ 官方确认页核对（C436 南京→江都 09:03 到，二等座）→ 勾选乘车人、选座 F → 确认 → **官方订单生成（PENDING_PAYMENT），用户在官方渠道可见**。

现场发现并修复的关键问题：
1. 下单登录态独立过期（约 1~2 小时，checkUser flag=false）：账户页在线≠可下单；已加启动/预热双重校验与抢票自动恢复登录；
2. 确认按钮倒计时（btn92 灰→btn92s 橙才绑定处理函数）：过早点击是静默空操作；已等类名就位再点；
3. 在线选座弹窗（已选座0/1）：必须处理，支持配置座位偏好（A/B/C/D/F）；
4. 结果分类误报：页面固定帮助文字含“证件”等关键词，改为只对提交后新增文本分类；
5. GUI 线程未加载保存会话（remember 缺失）导致“刚登录却提示未登录”。

首次真实提交必须在用户监督下进行（有真实出行需求、可接受下单后 30 分钟内完成支付或取消）：配置任务（passenger_refs=真实姓名）→ unlock → authorize → `order submit --adapter browser` → 核对官方未完成订单页 → 支付或取消。验收通过后 capability matrix 才将“真实下单”标为已验证。

### GUI 与引擎的并发约束（已实现并验证）

- 监控线程独占实例锁；监控运行期间其他引擎操作（查询/下单/登录）会被明确拒绝。
- UI 线程只做短连接数据读写；引擎操作在后台线程内创建自己的 Application 与浏览器对象。
- 通知经 outbox → Qt 信号 → 托盘气泡。
