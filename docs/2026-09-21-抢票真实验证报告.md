## 三、下单登录态说明（非缺陷）

- `whoami`（账户页）→ `AUTHENTICATED`，但 `check_booking_login()`（官方 `checkUser` flag）→ `False`。
- 这是 12306 的规则：账户页在线 ≠ 可下单，下单态约 1~2 小时独立过期。
- 要完成真实下单，需用户本人扫码重新登录刷新下单态。
- 抢票模式已内置"登录失效自动打开登录窗等待扫码后继续"的逻辑（本次已观察到该分支被触发）。

## 四、发现的缺陷：`sale-time fetch` 恒返回 null

- `_pick_sale_time()` 要求显式传入 `sale_date`，否则返回 `None`（为避免把起售时间错误拼到乘车日）。
- 但唯一调用点 `BrowserRailwayAdapter.query_sale_time()` **从不传 `sale_date`**，因此
  `sale-time fetch` 永远返回 `sale_time: null`（本次对 2026-09-25、2026-10-20 均为 null）。
- 回归审计 R09 把"返回 None"判定为 PASS，说明这是刻意的安全取舍（不推算开售日历日）。
- 影响：README 中"真实起售时间"能力实际不可用；抢票必须改用 `sale-time set` 手动登记或任务里填 `sale_at`。
- 建议：①在文档中明确 `sale-time fetch` 只读回缓存规则、不产出具体开售时刻；或 ②补上 sale_date 的可靠来源。

## 五、安全边界（使用前须知）

- 抢票模式命中后会**真实提交订单**：`booking.submit()` → 点击 `#submitOrder_id` / `#qr_submit_id`。
- `precheck_and_prepare()` 与 `prepare_order()` 是只读的（只落本地尝试、只打开确认页核对），
  只有 `submit()` 会真正生成订单。
- 抢票模式必须显式开启 `auto_submit` 且已登记授权快照；config 校验强制白名单车次非空。
- **风险点**：若结果页观察器白名单为空，`__ra_trains` 会退化为"任意车次"，可能命中非目标车次。
  抢票模式已有 config 校验兜底，但其他调用路径需注意。
