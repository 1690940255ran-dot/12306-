```
[12:10:39] 等待预热窗口（12:40），每 3 分钟保活
[12:13:44 … 12:37:45] 登录保活正常（10 次）
[12:40:00] 预热：打开官方结果页                      ← 准点
[12:40:01] 页面已预热；到点查询；期间每 3 分钟继续保活登录   ← 修复①生效
[12:40:02] 登录保活正常                              ← 修复②（预热后立刻校验）
[12:43:02] 登录保活正常                              ← 修复③（预热到开售不断档）
[12:45:01] 命中 G531 二等座！开始下单…                ← 开售 1 秒内命中
[12:46:15] 下单耗时：预检 0.12s，确认页+提交 73.21s
```

且**无**验证码/核验/繁忙/排队字样 → **就是会话被登出**，不是风控提示。

今天保活在 **12:43:02 仍返回正常**（距开抢仅 2 分钟，没有断档），12:45 点"预订"时却已登出。

**真凶仍未确定**，待查假设：

2. 2 秒高频刷新触发风控导致登出；
3. 账号在别处（手机 App）登录导致网页会话失效。

（票并未卖完：12:48 复查 10-07 北京南→上海虹桥仍有 **45 个车次**二等座可购。）

## 三、加固：命中后会话失效 → 自动扫码并重试一次

**痛点**：失败时用户就坐在电脑前，却只能看着工具放弃。

**新增行为**（`application/rush_service.py` + `application/booking_service.py`）：

命中后若下单失败，**且同时满足**下面两个条件，就打开官方登录窗等扫码，登录成功后**重试一次下单**：

1. 失败原因是"确认页都没打开"（`prepare_error`）——即**官方侧尚未收到任何提交动作**；
2. 复检确认登录确实失效（`check_booking_login()` 为 false）。

任一条件不满足则**绝不重试**，直接转人工——宁可不抢，也绝不冒险重复下单。

重试前的清理：调用新增的 `BookingService.abandon_unsubmitted()`，它只在仓库能确定
"该尝试不可能已在官方产生订单"时才放弃该记录（复用 `attempt_may_have_created_order`），
从而释放被占住的购票目标（否则 DB 唯一索引会拦住新尝试）。

重试时使用 `use_current_page=False`：重新登录后浏览器已离开结果页，必须重新导航。

## 六、新假设：预热"未开售"的日期会让会话被登出（正在验证）

三次真实记录放在一起，**唯一差异是"预热时目标日期是否已开售"**：

| 记录 | 预热目标 | 预热时状态 | 结果 |
| --- | --- | --- | --- |
| 9-22 12:45 真实抢票 | 10-06 | **未开售**（席别格 `*`） | ❌ 开抢时已登出 |
| 9-23 12:45 真实抢票 | 10-07 | **未开售**（席别格 `*`） | ❌ 开抢时已登出 |
| 9-23 17:56 演练 | 10-05 | **已开售** | ✅ 确认页 2.39s 打开成功 |

且 9-21 已证明：**只跑保活（不做别的）可连续 5 小时不掉线** → 保活本身不是元凶。

**假设**：预热（加载结果页）一个"还没开售"的日期，会让 12306 把该会话判为异常并登出
（查询超出可售范围的日期很像爬虫行为）。

**实验**（`.runtime/experiment_session_loss.py`，只读、不下单）：
1. 第 1 段（对照）：预热**已开售**的 10-07 → 每 3 分钟保活 → 观察 15 分钟；
2. 第 2 段（实验）：预热**未开售**的 10-08 → 每 3 分钟保活 → 观察 15 分钟。

**判定**：第 1 段存活 + 第 2 段掉线 → 假设成立。

**若成立，修法**：开售前**不预热目标日期**——改为预热一个**已开售**的日期来暖场，
到点再切到目标日期（依然全程无人值守；代价是开售瞬间多一次页面导航）。

> 承诺：实验结论出来之前不再声称"已修复"。

### 实验结果（13:26）：**假设被推翻** ❌

```
第 1 段（对照·已开售 10-07）：预热后 True → 12:59/13:02/13:05/13:08/13:11 保活全部正常 → 存活
第 2 段（实验·未开售 10-08）：预热查询异常（20s 超时，无车次行）→ 保活 5 次全部正常 → 存活
结论：预热"未开售"日期并不会让会话掉线。
```

## 八、新推断（有日志依据）：会话是在"点预订"那一刻失效的

回看 9-23 12:45 的日志，有一个之前被忽略的细节：

```
[12:45:01] 命中 G531 二等座！开始下单…
[12:46:15] 下单耗时：预检 0.12s，确认页+提交 73.21s
```

**预检 0.12s 通过** → 说明 `check_booking_login()`（checkUser）在命中那一刻**仍然有效**。
会话不是在开抢前死的，而是**在"点预订"这一步才失效**。

**推断机制**：开售瞬间表格刚重渲染，页面内 MutationObserver 在 **DOM 更新中途**就置位
（所以命中比官方渲染完成更早）；此时立刻点"预订"，很可能点到**尚未刷新完的行**——
该行 `onclick` 里带的还是**放票前的 token**。服务端拒绝这个过期 token，
并顺带把会话一起作废（页面随后显示"请登录注册"、checkUser 变 false）。

## 九、本次改动（基于上述推断）

1. **新增配置 `post_hit_settle_seconds`（默认 1.5，范围 0~10）**
   命中后、点击"预订"前先等待这段时间，让表格渲染完成，避开"点到旧行 token"的竞态。
2. **点"预订"前显式记录一次会话校验结果**
   `点"预订"前会话校验：True/False` —— 用于精确判定会话到底死在哪一步。
3. 回归：**166 项单测 + 16 项回归审计全 PASS**。

> 这是**推断驱动的改动**，不是已验证的修复。17:00 的真实放票（江都→南京 10-07，江都站起售 17:00）
> 会给出结论：若这次成功，说明竞态推断成立；若仍失败，日志里的"点预订前会话校验"会告诉我们
> 会话是在等待期间就死了、还是确实死在点击那一刻。
